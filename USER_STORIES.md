# User Stories и требования к системе

## 1. Проблема

В компьютерных классах колледжа информация об оборудовании хранится разрозненно. При перемещении техники, передаче в ремонт или списании записи могут устаревать. Приложение должно обеспечить единый локальный список инвентаря с поиском и сохранением изменений.

## 2. Карточка оборудования

| Поле | Тип | Обязательное | Правило |
|---|---|---:|---|
| `id` | целое число | да | положительное, уникальное; назначается автоматически |
| `type` | строка | да | не пустая, минимум 2 символа |
| `name` | строка | да | не пустая, минимум 2 символа |
| `room` | строка | да | не пустая, минимум 1 символ |
| `status` | строка из набора | да | `исправно`, `требует ремонта`, `списано` |
| `created_at` | ISO 8601 | да | автоматически при добавлении |
| `updated_at` | ISO 8601 | да | автоматически при добавлении и изменении |

Первичный ключ — `id`. При добавлении приложение присваивает следующий номер: максимальный существующий `id` + 1. Поле `id` не редактируется.

## 3. Формат хранения

Данные хранятся в `data/inventory.json`:

```json
{
  "version": 1,
  "items": [
    {
      "id": 1,
      "type": "Монитор",
      "name": "Samsung S24",
      "room": "204",
      "status": "исправно",
      "created_at": "2026-09-01T09:15:00+03:00",
      "updated_at": "2026-09-01T09:15:00+03:00"
    }
  ]
}
```

Приложение читает и старый формат JSON-массива. Для старых записей без `updated_at` это поле при загрузке заполняется значением `created_at`.

## 4. Правила валидации

- Все текстовые поля обрезаются по краям и не могут быть пустыми.
- `type` и `name` должны содержать не менее двух символов; `room` — не менее одного.
- `status` может принимать только три перечисленных значения. В интерфейсе также доступны сокращённые варианты `1`, `2`, `3`.
- `id` назначается приложением, должен быть положительным целым числом и не повторяться.
- Ошибки структуры и синтаксиса JSON приводят к понятному сообщению; исходный повреждённый файл не перезаписывается молча.
- Изменение данных сохраняется после каждой успешной операции.

## 5. User Stories и критерии приёмки

### US-01. Просмотр оборудования
Как лаборант, я хочу видеть список оборудования, чтобы быстро оценивать наличие и состояние техники.

Критерии:
- отображаются номер, тип, наименование, кабинет, состояние и дата добавления;
- при пустом списке выводится «Список пуст»;
- просмотр не изменяет данные.

### US-02. Добавление оборудования
Как лаборант, я хочу добавлять новую единицу техники, чтобы фиксировать поступление оборудования.

Критерии:
- приложение запрашивает тип, наименование, кабинет и состояние;
- номер назначается автоматически и не дублируется;
- пустые и слишком короткие значения отклоняются;
- состояние проверяется по допустимому набору;
- после добавления запись появляется в списке и сохраняется в JSON.

### US-03. Поиск оборудования
Как лаборант, я хочу искать оборудование по разным полям, чтобы быстро находить нужную запись.

Критерии:
- доступны поиск по номеру, типу, наименованию, кабинету и состоянию;
- поиск нечувствителен к регистру и находит подстроку;
- при отсутствии совпадений выводится понятное сообщение;
- поиск не изменяет записи.

### US-04. Изменение записи
Как лаборант, я хочу обновлять сведения об оборудовании, чтобы данные отражали его актуальное состояние и местоположение.

Критерии:
- запись выбирается по инвентарному номеру;
- можно изменить тип, наименование, кабинет и состояние;
- номер не редактируется;
- пустые значения и недопустимое состояние отклоняются;
- после успешного изменения обновляется `updated_at`, данные сохраняются.

### US-05. Удаление записи
Как лаборант, я хочу удалять запись после подтверждения, чтобы исключать её из текущего списка учёта.

Критерии:
- перед удалением показываются номер и наименование;
- `y` подтверждает удаление, любой другой ответ отменяет;
- несуществующий номер обрабатывается без аварийного завершения;
- после удаления запись отсутствует в списке и в сохранённых данных.

### US-06. Сохранение между запусками
Как пользователь, я хочу, чтобы изменения сохранялись, чтобы не вводить данные повторно.

Критерии:
- при старте данные загружаются из JSON;
- отсутствующий файл создаётся автоматически;
- пустой файл трактуется как пустой список;
- повреждённый или некорректный файл не перезаписывается молча;
- добавление, изменение и удаление сохраняются;
- старые записи без `updated_at` поддерживаются.

## 6. Примеры данных

В `data/inventory.json` включено 10 демонстрационных записей с разными типами оборудования, кабинетами и состояниями. Их можно использовать для проверки просмотра, поиска и фильтрации вручную.

## 7. Итоговый статус

Функции, заявленные в US-01…US-06, реализованы в коде проекта. Автоматические проверки находятся в `tests/`. Результаты фактического запуска тестов отражены в `TEST_REPORT.md`.

Ограничения:
- графический интерфейс отсутствует;
- данные хранятся локально в JSON, без СУБД;
- параллельная многопользовательская работа не поддерживается;
- повреждённый JSON требует ручного исправления или восстановления из резервной копии;
- автоматического резервного копирования нет.
